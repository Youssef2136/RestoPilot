# Authorization and Data-Integrity Requirements Checklist: Restaurant and Branch Management (Phase 3)

**Purpose**: Reviewer assessment of the requirements quality of this phase's two load-bearing surfaces — the authorization/isolation boundary and the validation, state-integrity, and failure-semantics rules — before implementation begins. Every item tests what the specification writes down (or omits) in `spec.md`; none of them tests whether behavior works.
**Created**: 2026-09-16
**Feature**: [spec.md](../spec.md) — FR-001…FR-025, SC-001…SC-007, user stories 1–5
**Depth**: Standard | **Audience**: Reviewer (pre-implementation requirements review) | **Focus**: (1) security and authorization surface; (2) data-integrity, validation, and failure-semantics surface.

**Note**: This custom checklist is generated by the `$speckit-checklist` command based on feature context and requirements.
**Review Ownership**: This checklist is a reviewer-owned requirements-quality review artifact. Mark an item `[x]` only when the reviewer determines the requirements-quality criterion is satisfied.
**Marker Semantics**: `[x]` means the criterion has been reviewed and satisfied for requirements quality. It does not mean implementation work is complete.

## Authorization and Role Scope

- [ ] CHK001 Are owner-only requirements stated for every management action this phase introduces (restaurant profile, settings, branch creation and editing, working hours, tables, staff assignment, QR obtainment)? [Completeness, Spec §FR-006, §FR-018]
- [ ] CHK002 Is the role vocabulary used for authorization ("the restaurant's owners", "an owner", "branch manager", "cashier", "kitchen") consistent across user stories, functional requirements, and acceptance scenarios? [Consistency, Spec §FR-002, §FR-006, US4]
- [ ] CHK003 Is the boundary between branch managers' feature 003 read/operational scope and this phase's management actions stated explicitly per surface, so a reviewer can tell which actions are deliberately out of their reach? [Clarity, Spec §FR-006, US2 scenario 5]
- [ ] CHK004 Is "denied at the trusted data layer" specified in a way that distinguishes it from interface-only hiding, so acceptance can be judged without reading implementation artifacts? [Clarity, Spec §FR-005; Constitution §IV]
- [ ] CHK005 Are the authorization requirements for restaurant creation stated precisely — a linked-profile caller, membership-less callers explicitly admitted, and the creator becoming owner? [Completeness, Spec §FR-001, Assumptions]
- [ ] CHK006 Is the platform super-admin denial stated for every management surface and access path, rather than only as a general capability statement? [Coverage, Spec §FR-021]
- [ ] CHK007 Is "through every access path" (the denial requirement's scope) defined well enough that a reviewer can list what must be covered, or is the term left ambiguous? [Ambiguity, Spec §FR-005, §FR-022]
- [ ] CHK008 Is QR obtainment's authorization requirement consistent with the QR's restaurant-level scope (the restaurant's owner, not branch-scoped roles)? [Consistency, Spec §FR-018, US5 scenario 3]
- [ ] CHK009 Are authorization decisions defined against the actor's memberships as they stand at access time, covering multi-membership, role change, and removal states? [Completeness, Spec §FR-015, §FR-017]
- [ ] CHK010 Is the staff-list visibility rule of feature 003 (owners and branch managers read; cashiers and kitchen cannot) restated as an unchanged requirement over this phase's new surfaces? [Completeness, Spec §FR-025, Assumptions]

## Tenant and Branch Isolation

- [ ] CHK011 Are cross-tenant denials required for every new configuration surface this phase adds (profile, settings, branches, working hours, tables, staff, QR)? [Coverage, Spec §FR-022, §FR-025]
- [ ] CHK012 Is "a branch-scoped member sees exactly their assigned branch's scope" specified per surface, including that other branches of the same restaurant remain unreachable? [Completeness, Spec §FR-017, US2 scenario 5]
- [ ] CHK013 Is "cross-tenant references stay impossible" stated as an invariant that can be checked independently of interface behavior? [Measurability, Spec §US2 scenario 6, §FR-025]
- [ ] CHK014 Are the public and unauthenticated access requirements for this phase's new data explicitly deny-by-default, with only the existing public entry surface remaining public? [Coverage, Spec §FR-019, §FR-025]
- [ ] CHK015 Does the spec state what a denied request may reveal about out-of-scope resources (existence, names, identifiers), or is that left to implementation interpretation? [Gap, Spec §FR-005]

## Validation and Rejection Semantics

- [ ] CHK016 Are the restaurant creation fields enumerated with which values are required and which are optional? [Clarity, Spec §FR-001, §FR-002]
- [ ] CHK017 Is "malformed public identifier" quantified with explicit format rules, rather than left to later artifacts to interpret? [Ambiguity, Spec §FR-001, §FR-004]
- [ ] CHK018 Are duplicate-public-identifier rejection requirements stated for both the creation and the change paths? [Completeness, Spec §FR-001, §FR-004]
- [ ] CHK019 Are the working-hours rejection conditions enumerated exhaustively (zero-length interval and same-day overlap), with the touching-boundary case explicitly permitted? [Completeness, Spec §FR-008]
- [ ] CHK020 Is a zero-length interval defined distinctly from a post-midnight interval (for example 10:00–10:00 vs 18:00–02:00), so the two cannot be conflated during acceptance? [Clarity, Spec §FR-008, Edge Cases]
- [ ] CHK021 Is the scope of overlap rejection unambiguous for post-midnight intervals — whether real-time overlaps across intervals recorded under different days are rejected or deliberately accepted? [Ambiguity, Spec §FR-008]
- [ ] CHK022 Are table-label validation rules defined for whitespace-only labels and for duplicates within the same branch? [Completeness, Spec §FR-010, Edge Cases]
- [ ] CHK023 Is the per-branch (not per-restaurant) scope of table-label uniqueness stated unambiguously? [Clarity, Spec §FR-010, US3]
- [ ] CHK024 Is the blank/whitespace rejection rule stated consistently across restaurant, branch, table, and person names? [Consistency, Edge Cases]
- [ ] CHK025 Is the last-owner safeguard defined for both removal and demotion, including the count-of-one boundary? [Completeness, Spec §FR-016]
- [ ] CHK026 Is "exact duplicate membership" defined (same restaurant, role, and branch) and distinguished from allowed additional memberships? [Clarity, Spec §FR-013, Edge Cases]
- [ ] CHK027 Are the role/branch consistency rules stated (branch-scoped roles require a branch of the same restaurant; the owner role must not carry one)? [Clarity, Spec §FR-013, Edge Cases]
- [ ] CHK028 Are validity requirements defined for the timezone setting, including unknown values rather than only missing ones? [Gap, Spec §FR-003]
- [ ] CHK029 Are contact-information validity requirements defined, or explicitly declared outside this phase's validation scope? [Gap, Spec §FR-002]
- [ ] CHK030 Is email-address validity for staff addition defined at the requirement level (syntactic plausibility vs. deliverability)? [Ambiguity, Spec §FR-013]

## State Integrity and Concurrency

- [ ] CHK031 Is table activation specified as explicit persisted state with defined transitions and a defined state for newly created tables? [Completeness, Spec §FR-011]
- [ ] CHK032 Is repeated-transition behavior (deactivating an inactive table, activating an active one) defined as state-neutral? [Clarity, Spec §FR-011, Edge Cases]
- [ ] CHK033 Is renaming an inactive table explicitly permitted, with its activation state preserved? [Coverage, Spec §US3 scenario 6]
- [ ] CHK034 Are concurrent-edit outcomes for configuration changes specified (each accepted change applied atomically; no partial or contradictory records)? [Coverage, Edge Cases; Constitution §VI]
- [ ] CHK035 Is the effective-access timing of membership changes ("next access") defined unambiguously for role changes, branch changes, and removals? [Clarity, Spec §FR-015]
- [ ] CHK036 Is the identifier-change consequence for entry URL and QR defined as one consistent requirement (the old identifier no longer addresses this restaurant and is not retained or encoded anywhere — no alias, no redirect, no history — while the artifact obtained afterwards encodes the new URL)? [Consistency, Spec §FR-004, §FR-018]
